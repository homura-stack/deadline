# Wave 7 browser-test failure investigation

## 調査範囲

`wave-k-browser.cjs` の `No safe approach to a Wave enemy` のみを調査。
ゲーム本体・Wave難易度・救済・セーブ処理は変更しない。commit / pushなし。

## 根本原因

テスト用経路探索の偽陰性が2種類あった。

1. **探索グラフがプレイ領域の下端を含まない。**
   ゲームの移動範囲はy=24〜576だが、旧16px格子・35行の最下行はy=568。
   実ブラウザのWave 7でPicoが `(57.8686, 568.0000)` にいる配置を捕捉。
   y=576側へ抜ければ通れるが、旧探索は出発点からつながる格子点を見つけられない。
   格子を8pxにした比較でも解決したが、最終修正は**16px間隔を維持し、正確な下端を含める**最小変更。
   同じ配置で全5体LOCK、危険区間0、被弾0、実シミュレーションによるWaveクリアを確認。
   この経路は旧テストの3px安全余白も完全に維持する。

2. **生存中のNear Miss位置を、探索用余白が閉じ込める。**
   ゲームの合計被弾半径は14px、探索用半径は追加余白3px込みの17px。
   STOP入力を50ms遅延した実ブラウザで、最寄り弾まで16.9911pxの生存状態を捕捉。
   出発点自体が17px円内にあるため、旧探索では全方向が拒否される。格子の細分化だけでは直らない。
   その弾についてだけ余白を出発時距離以下へ調整し、**14pxの実被弾半径は絶対に下回らない**。
   ほかの弾の3px余白は維持。同じ配置で危険区間0・全5体撃破を確認。

「経路なし」はゲーム本体の判定ではなく、Node側の不完全な探索のassertionだった。
捕捉した両ケースは `phase=stopped`、残り8.1秒、救済倍率1。ルート入力前の探索失敗であり、STOP時間切れではない。
本体にゲーム全般の問題がないと保証するものではないが、今回捕捉した2種類の失敗は本体で有効なクリア経路を証明できた。

## 5つの切り分け

| 観点 | 結論と根拠 |
|---|---|
| ゲーム本体の回帰 | 捕捉した失敗配置で本来の判定を通したクリアが可能。本体の変更は不要 |
| 探索アルゴリズム | 下端欠落と出発点の余白処理が直接原因。固定配置でも決定的に失敗 |
| ランダム性 | `simulation.js` はMath.randomを使用しない。seed固定は演出乱数を固定するだけで、戦闘の操作タイミングを固定しない |
| タイミング | 回避ヘルパーは4分割のマウス移動と90ms実時間待ち、ゲームはrequestAnimationFrameから1/120秒stepを回す。固定seedでもSTOP時刻・Pico位置・弾配置が変化する |
| 永続セーブ導入 | 専用ページで保存・復元呼び出しのみ無効化した比較でもWave 7失敗を再現。戦闘への意味的な依存はない。保存等の実行時間がスケジューリングへ全く影響しないとまでは断定しない |

永続セーブ導入比較はHTTPレスポンスを専用ブラウザ内だけで置換するアブレーション。
`game.js` の保存・復元呼び出しを除外し、Wave設定／本番ファイルは変更しない。
永続セーブ導入以前の完全なリビジョンとの比較ではない。新規ブラウザコンテキストで既存の進行セーブはない。
コード上も、この新規通しプレイでは復元処理はタイトル／START時だけで、Wave 1開始後にworldを再構築しない。
AREA境界の保存処理はworldの数値をコピーするだけで、敵・弾・ゲージへ書き戻さない。

## 再現実験

Chrome 152.0.7977.82、1366×900、固定seed `0xdead1e`、通常パラメータ、救済なし。
各実行は独立したページ／ブラウザでWave 1から実入力で進行。
実時間スケジューリングは固定していないため、以下は母集団の確定的な失敗確率ではなく、この環境での観測率。

| 修正前の条件 | Wave 7失敗 / 実行数 |
|---|---:|
| 通常 | 0 / 3 |
| 永続セーブ導入保存・復元呼び出し無効 | 1 / 3 |
| Wave 7のSTOP入力だけ50ms遅延 | 2 / 3 |

直前の永続セーブ導入検証での2回連続失敗は履歴として区別し、今回の分母に混ぜない。
成功したseedを選ぶ、失敗を再試行で隠す、ゲージ高速回復、制限時間延長、敵／弾移動、無敵化は行わない。
50ms遅延は原因切り分け用だけで、リリース回帰テストには追加しない。

修正後は通常 **0/3失敗**、50ms遅延 **0/3失敗**。6回ともWave 7を実入力でクリアした。

さらに旧`delay50-2`と修正後`fixed-delay50-1`は、Pico・敵・弾のJSON SHA-256が完全一致
（`e5d25659f247d7f24b600509a6341c62cea795fe5fa059924f1de1088d4fd9c1`）。
同じ物理配置で、旧版は探索失敗、修正版は実ブラウザのDRAW→EXECUTEで成功した。
単に成功するタイミングを引いたことだけを根拠にしていない。

| 同一STOPスナップショットの反復 | 旧探索の失敗 | 修正後の実シミュレーションクリア |
|---|---:|---:|
| 下端欠落ケース | 20 / 20 | 20 / 20 |
| Near Miss余白ケース | 20 / 20 | 20 / 20 |

いずれも全5体LOCK、危険区間0、被弾0、設定変更なし。固定状態の反復なので、実プレイ全般の成功率を意味しない。
数値とSTOP状態ハッシュは `tests/artifacts/wave-investigation/analysis.json` に記録。

## 修正と回帰保護

- `tests/route-planner.cjs`: 既存の探索をテスト専用の純粋モジュールへ分離。探索下端と余白だけ修正。
- `tests/browser.cjs`: 共通モジュールを利用。実際のpointer入力、STOP残時間、危険区間0、全対象LOCKのassertionは維持。
- `tests/wave-k-browser.cjs`: 探索失敗時にSTOPスナップショットを報告へ保存。クリア／無救済／config不変の検証は維持。
- `tests/route-planner.test.cjs`: 2種類の失敗をテスト先行で再現し、実境界での衝突拒否と実シミュレーションのクリアを検証。
- `tests/fixtures/wave7-grid-trap.json`, `tests/fixtures/wave7-padding-trap.json`: 実ブラウザから捕捉した変更なしのSTOP状態。
- 当時の一時調査ツールは公開ツリーには含めない。現在の再現確認には上記fixtureと経路探索回帰テストを使用する。
- 本文書。

調査時のログと比較用旧コードは `tests/artifacts/wave-investigation/`（Git管理外）に保存したもので、公開cloneには含まれない。以下の数値は当時の履歴であり、一時ツールを用いた実験全体の再実行手順ではない。

## 限界

有限格子・有限の敵接近候補を使う自動探索は完全な経路存在判定ではない。
今回の原因を直しても、将来の全配置に対する成功や体感難易度は保証しない。
今後同じassertionが出た場合は、保存したSTOP状態から切り分ける。難易度を下げて回避しない。
